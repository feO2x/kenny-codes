# CHACK: A Simple Way to Structure Software Applications

## TL;DR

**CHACK** is a simple model for structuring a single app. Every piece of code you write belongs to exactly one of four categories:

- **C**ore
- **H**umble Objects at the process boundary
- **A**utomated Tests
- **C**omposition Root

CHACK is based on aspects of Domain-Driven Design, Hexagonal Architecture, and Vertical Slice Architecture. It follows software principles like SOLID, DRY, Composition-Over-Inheritance, and KISS. It is easier to learn than these approaches and pushes junior developers into the pit of success.

Oh, and the **K** in CHACK is for **K**enny - which conveniently lets you pronounce it like "Chuck".

## CHACK overview

<ChackDiagram />

- **The Core** is everything that runs in memory: your domain model, your services, your DTOs, your validators. It holds the logic that makes the software worth building, and it never performs an I/O call itself. When it needs one, it goes through an abstraction that belongs to the Core.
- **Humble Objects** sit at the process boundary and take care of data access. Each one does two things: perform the actual I/O calls to one third-party system, and map the data going out and coming back. They follow the [Humble Object pattern](http://xunitpatterns.com/Humble%20Object.html) from Gerard Meszaros' [xUnit Test Patterns](http://xunitpatterns.com/).
- **Automated Tests** follow the [test pyramid](https://martinfowler.com/bliki/TestPyramid.html). Unit Tests exercise the Core with Humble Objects replaced by in-memory Test Doubles, which is why thousands of them run in seconds. Integration and End-to-End Tests cover the happy path and wiring against third-party systems and act as a second line of defense against regression.
- **The Composition Root** assembles the pieces at startup - usually with a DI container and configuration from files, environment variables, and command-line arguments. It is described in depth in Mark Seemann's and Steven van Deursen's [Dependency Injection Principles, Practices, and Patterns](https://www.manning.com/books/dependency-injection-principles-practices-patterns).

Most arrows in the diagram are compile-time dependencies, like in UML:

- an open arrowhead means one category **references** another
- a dashed line with a hollow triangle means one type **implements or derives from** another

The Composition Root knows the Core; the Core does not know the Composition Root. Humble Objects and Test Doubles implement the I/O abstractions. The abstractions themselves belong to the Core according to the [Dependency Inversion Principle](https://www.labri.fr/perso/clement/enseignements/ao/DIP.pdf), which is why both boxes carry the brand gradient. The one double-headed arrow on the left represents I/O calls happening at runtime.

The placements along the process boundary are deliberate. The Humble Objects box sits **on** the boundary, because they make outgoing calls or receive incoming ones. Integration Tests **straddle** the boundary: they may exercise the system under test inside or outside the test runner process. End-to-End Tests sit **outside**, to the right of the boundary, because they usually start the system under test in another process (e.g., via Docker Compose). Unit Tests and their Test Doubles stay inside the test runner process. Every category may also use the frameworks and libraries it references, so those arrows are left out to keep the picture readable.

All of this can happen in a single project, and **CHACK encourages you to keep the number of projects in your codebase small**.

## The problem CHACK solves

Codebases get hard to maintain at two extremes.

<DesignTensionDiagram />

At one extreme, **too little abstraction** produces "Spaghetti Code". Too many responsibilities accumulate in a single type: business rules become tangled with calls to third-party systems (e.g., with SQL statements and HTTP calls), files grow to thousands of lines, and even simple tests require a database. Every change becomes risky because parts of the code can't be tested in isolation.

**Excessive abstraction** sits at the opposite extreme. Applying principles like SOLID and design patterns mechanically produces dozens of interfaces and tiny classes, plus layers of indirection. The code may be loosely coupled, yet understanding a single domain behavior requires tracing it across half a dozen abstractions.

CHACK avoids both extremes with two rules:

- **Abstract I/O at the process boundary.** For each third-party system used **in a given context**, define a Core-owned abstraction and implement it with a Humble Object. Tests can replace the Humble Object with a Test Double, allowing the Core logic to run entirely in memory.
- **Use abstractions selectively inside the Core.** Core types are tightly coupled by default. Introduce an interface or abstract base class only when it serves a concrete purpose - multiple meaningful implementations are often a good indication. An endpoint service, for example, may call its validator directly; one Unit Test can cover both without a Test Double.

:::info[The main idea behind CHACK]
**CHACK forces you to clearly distinguish between in-memory and I/O calls.** Make the blue Core box as large as possible to have more code that in-memory Unit Tests can target.

Why? Third-party system calls are a billion times slower than your in-memory calls and may fail way more often. Take a look at [the performance costs on the Automated Tests page](./automated-tests.mdx#performance-costs-of-integration-tests).

CHACK does not tell you how to design within the four categories. You want to use the Mediator pattern in your codebase? Go ahead. CQRS, event sourcing, a rich domain model, an anemic one? All compatible with CHACK.
:::

## A methodology, not a framework

There is nothing to install. CHACK is a way of introducing the right seams in your codebase. It works the same in an ASP.NET Core service, an Angular app, a WPF app, or a console tool. If you can answer "Which of the four categories does this piece of code **exclusively** belong to?", you are doing it.

Because most of my work is in .NET, the concrete examples are C#. To keep the model itself language-neutral, these docs come in two parts:

- **The methodology** - the pages in the main section. They hold for any language and any framework.
- **[CHACK in .NET](./dotnet/index.md)** - a section of its own that shows how the model looks in the stack I use every day: ASP.NET Core, Entity Framework Core, and the .NET base class library.

## Why CHACK?

You might be wondering why you should care about CHACK. There are already many approaches to designing software, like Hexagonal Architecture, Domain-Driven Design, or Clean Architecture. CHACK doesn't bring particularly new things to the table. It is rather a distillation of patterns and approaches which can be easily taught, especially to junior developers.

How many books do you need to read, or tutorials do you need to watch, to understand and apply Hexagonal Architecture or Clean Architecture? I think CHACK is so condensed that it can be easily taught in 4 to 8 hours. You can start applying it without any frameworks or project templates. Apply it to parts of your codebase and see the benefits. Start small and grow over time.

## Sources

CHACK stands mainly on four books:

- Eric Evans, [Domain-Driven Design](https://www.oreilly.com/library/view/domain-driven-design-tackling/0321125215/) - the ubiquitous language, the isolated domain (the Core) and the patterns that shape the Core: Entities, Value Objects, and Aggregates.
- Martin Fowler et al., [Patterns of Enterprise Application Architecture](https://martinfowler.com/books/eaa.html) - the catalog for Line-of-Business software: domain models, O/R mapping, units of work, data transfer objects, among other patterns.
- Steven van Deursen and Mark Seemann, [Dependency Injection Principles, Practices, and Patterns](https://www.manning.com/books/dependency-injection-principles-practices-patterns) - the Composition Root and its Register-Resolve-Release phases.
- Gerard Meszaros, [xUnit Test Patterns](http://xunitpatterns.com/) - the Humble Object pattern, the four-phase test, and the vocabulary for Test Doubles.

Robert C. Martin's [Clean Architecture](https://www.oreilly.com/library/view/clean-architecture-a/9780134494272/) is worth adding: chapter 23 describes Humble Objects at the process boundary and arrives at much the same place from a different direction. For organizing code around features, CHACK borrows from Jimmy Bogard's [Vertical Slice Architecture](https://www.jimmybogard.com/vertical-slice-architecture/).
