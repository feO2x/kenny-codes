# Humble Objects at the Process Boundary

<ChackDiagram highlight="humble-objects" />

## Why the boundary needs its own category

No application does anything useful without I/O. Databases, the file system, web services, message brokers, printers, CRMs, ERPs, SAP, you name it. Every one of them lives outside your process, and reaching them usually costs a billion times more time than an in-memory call. See the [Automated Tests Page](./automated-tests.mdx#performance-costs-of-integration-tests) for the numbers.

Cost is only half of it. I/O is also where most exceptions come from, and the hardest part of your code to exercise in Automated Tests: a third-party system must be running, populated with the right state before the test and reset afterwards. Provoking failures on demand can be hard or outright impossible. Code that mixes business rules with I/O inherits all of that difficulty. Entangling both is the main reason for "Spaghetti Code" in my opinion.

So CHACK isolates I/O from the Core. Humble Objects sit at the process boundary: for each use case, they represent the glue between your data access technology and the Core. Each Humble Object should talk to one third-party system. They implement an [I/O abstraction owned by the Core](./the-core.mdx), which means you can introduce a Test Double for it in Unit Tests and stay in memory.

## The duties of a Humble Object

1. **It performs the I/O calls.** You usually use a data access technology like an Object-Relational Mapper (ORM), an HTTP client, a broker client, a CLI tool, or proprietary SDKs/drivers to access the third-party system. Aim for one I/O call per method on the Humble Object, though in certain use cases, more than one call can occur.
2. **It registers entity changes, if needed.** If your data access technology supports change tracking, some methods on the Humble Object may need to add entities to or remove them from the ORM's Unit of Work. The capabilities of your data access technology shape the API of the Humble Object.
3. **It maps the data.** Outgoing parameters get translated into whatever the third-party system expects, and incoming data gets translated into the types the Core wants back. This can include catching exceptions and turning them into a result value (e.g., with the Result Pattern) or into an exception the Core understands (although throwing again comes with performance costs).

:::info[Light.PortableResults]
I have implemented my own Result Pattern library called Light.PortableResults. Check it out on [GitHub](https://github.com/feO2x/Light.PortableResults)!
:::

That is the whole list. Everything else, like decisions, validation, calculation, orchestration, or logging, belongs to the Core.

When it comes to mapping, there are two cases:

- **The framework does it for you.** An ORM materializing entities from a query, or a serializer turning a body into a DTO, is mapping you did not write. Cover it in Integration and End-to-End Tests.
- **You write it yourself.** The easiest was is to place the self-written mapping logic in the Humble Object as a private method. If it's complex enough to deserve its own tests and can easily run in-meomory, move it into the Core as a static mehhod and cover it with Unit Tests (this largely depends on certain framework/library types being easy to instantiate.). What stays in the Humble Object is the I/O call plus a delegation to the mapper.

The rule of thumb: **make the Core as large as possible and the Humble Object as small as possible**. If you find yourself wanting a test for something inside a Humble Object, that something likely belongs in the Core.

## Guidelines

- **Keep them boring.** Avoid branches and loops. A Humble Object that needs an `if` for anything other than a precondition check is usually hiding a decision that belongs in the Core.
- **One Humble Object per third-party system, per vertical slice.** Where the target system supports transactions, a Humble Object is representing a Unit of Work or one connection to one third-party system. Do not access two different systems within one Humble Object.
- **One method per interaction.** Target one I/O call per method. On rare occasions, multiple I/O calls per Humble Object method can make sense. If the technology supports asynchronous calls, avoid designing these methods synchronously unless your Thread Pooling mechanism can handle it.
- **No validation.** A Humble Object returns DTOs or domain objects; the Core validates them if validation is required. Data coming back from a third-party system is input like any other. Some Data Access frameworks might validate internally.
- **Unify at the boundary, if you must.** If the same data lives in two systems with slightly different shapes - for example, two DBMS with different table layouts - the Humble Objects may normalize both into the same Core type. That is mapping, and it is allowed.
- **Release resources deterministically.** Humble Objects usually own resources that must be released: a connection, a transaction, a stream, or a file handle. Expose that release operation on the I/O abstraction as well, so callers can clean up the Humble Object without knowing its concrete type. In most apps, the [Composition Root](./composition-root.mdx) handles disposal at the end of a request or message; without a DI container, the caller does it. The [Clients and Sessions](./clients-and-sessions.md#releasing-clients-and-sessions) page shows how this works in detail.
- **The same rules apply to UI code.** A view is a Humble Object: it renders and it forwards user interactions. Keep bindings simple, avoid multi-bindings and view-specific converters that carry logic, keep animation triggers dumb, and put no logic in printed reports. Anything you move out of the view is something you can unit-test.
- **Return results, not deferred queries.** Returning a query object that the caller can extend and execute later pulls data-access decisions back into the Core. Materialize the results inside the Humble Object so the I/O stays in one place.

## Clients and Sessions

Humble Objects called by the Core come in two flavors, depending on who controls the transaction:

- A **Client** is used when the Core does not control transactions. A Client may still use a transaction internally - for a single query, or for its whole lifetime - but it never hands it to the Core.
- A **Session** is used when the Core controls a transaction. It offers a method to commit, and releasing it without committing rolls back all changes.

A Humble Object that only reads data and offers no commit method is therefore a Client, not a Session. [Clients and Sessions](./clients-and-sessions.md) covers both in detail.

## Scope and sharing

Each vertical slice gets its own Humble Object per third-party system. This matters most when transactions are involved, because a Session then marks the transaction boundary of exactly one feature.

You may know a different approach from the Repository pattern, where one interface collects every operation on an entity across all features. Such an abstraction is shaped by the data instead of by its consumer, which works against the Dependency Inversion and Interface Segregation Principles: every consumer depends on members it doesn't need, and every Test Double has to implement them. [Clients and Sessions](./clients-and-sessions.md#one-per-slice-not-one-per-entity) compares the two approaches.

Two or more slices can share a Humble Object when they need the exact same abstraction. If their needs diverge later, split it again.

Keeping Humble Objects separate doesn't mean duplicating code. Shared queries, filters, projections, or mappings can move into static methods that each affected Humble Object can call. [Hierarchy and sharing](./vertical-slices.md#hierarchy-and-sharing) explains which folder to put them in. Static methods that perform I/O belong to the Humble Object category; static methods that run purely in memory belong to the Core.

## The local file system is I/O, too

Reading and writing files is still I/O, even though the local file system is always available. The same goes for libraries that operate on files on behalf of the Core, such as document converters or image processors. Put file access behind an I/O abstraction as well. Your Unit Tests may still touch the local file system (see [Automated Tests](./automated-tests.mdx)), and a Test Double lets you simulate disk errors that are hard to provoke on demand: a locked file, a full drive, or a corrupt document.

## Supporting types

Not every type in this category is called by the Core. A database context subclass, a base class for Humble Objects, a static helper method that performs I/O, or a startup task that creates database indexes all perform I/O, which puts them in the Humble Object category even though they don't implement a Core abstraction. The same guidelines apply: keep them small and free of business logic.

## Where the pattern comes from

Michael Feathers published *The Humble Dialog Box* in 2000. He had built a modal dialog with the logic baked into the window, then found he could not test it without spinning up a UI thread and initializing the whole UI framework first. His fix was to move the logic into a separate class and leave the dialog with nothing but its interactions with the framework - the dialog became humble.

[xUnit Test Patterns](http://xunitpatterns.com/) generalized this into the [Humble Object pattern](http://xunitpatterns.com/Humble%20Object.html): the Humble Object holds the logic that is hard to unit-test and delegates everything else to a testable component.

> Each time the Humble Object is called by the framework, it delegates to the testable component. If the testable component needs any information from the context, the Humble Object is responsible for retrieving it and passing it to the testable component. The Humble Object code is typically so simple that we often don't bother writing tests for it because it can be quite difficult to set up the environment need to run it.

Robert C. Martin arrives at the same conclusion in chapter 23 of [Clean Architecture](https://www.oreilly.com/library/view/clean-architecture-a/9780134494272/), where Humble Objects at the process boundary keep business logic free of I/O.
