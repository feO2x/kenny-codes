# Humble Objects at the Process Boundary

<ChackDiagram highlight="humble-objects" />

## Why the boundary needs its own category

No application does anything useful without I/O. Databases, the file system, web services, message brokers, printers, CRMs, ERPs, SAP, you name it. Every one of them lives outside your process, and reaching them costs usually a billion times more time than an in-memory call. The [Automated Tests](./automated-tests.mdx) page has the numbers.

Cost is only half of it. I/O is also the main part of your code that causes exceptions and that is the hardest to exercise in Automated Tests: a third-party system must be running, populated with the right state before the test and reset afterwards. Provoking failures on demand can be hard or outright impossible. Code that mixes business rules with I/O inherits all of that difficulty, entangling both is the main reason for "Spaghetti Code" in my opinion.

So CHACK isolates I/O from the Core. At the process boundary sit Humble Objects: for each use case, they represent the glue between the your Data Access technology and the Core. Each Humble Object should talk to one third-party system. They implement an [I/O abstraction owned by the Core](./the-core.mdx), which means you can introcude a Test Double for it in Unit Tests and stay in-memory.

## The responsibilities of a Humble Object

1. **It performs the I/O calls.** You usually use a data access technology like an O/R mapper, an HTTP client, a broker client, invoking a CLI process, or proprietary SDKs/drivers to access the third-party system. Aim for one I/O call per method on the Humble Object, though in certain use cases, more than one call can occur.
2. If your data access technology supports Change Tracking, some methods on the Humble Object may be required to add or remove entities from, e.g., a `DbContext`. The capabilities of your Data Access technology shapes the API for the Humble Object.
3. **It maps the data.** Outgoing parameters get translated into whatever the third-party system expects, and incoming data gets translated into the types the Core wants back. This can involve catching exceptions which then can be mapped to, e.g., the Result Pattern or wrapped in another exception the Core understands.

:::info[Light.PortableResults]
I have implemented my own Result Pattern library called Light.PortableResults. Check it out on [GitHub](https://github.com/feO2x/Light.PortableResults)!
:::

That is the whole list. Everything else like decisions, validation, calculation, orchestration, or logging belongs to the Core.

Two notes on mapping the data:

- **The framework does it for you.** An O/R mapper materializing entities from a query, or a serializer turning a response body into a DTO, is mapping you did not write. Cover it in Integration and End-to-End Tests.
- **You write it yourself.** You might simply leave it in the Humble Object as a `private` method. If you are able to unit-test it easily, you might move it into a `public static` method on a different type, belonging to the Core. What stays in the Humble Object is the call plus a delegation to the mapper.

The rule of thumb: **make the Core as large as possible and the Humble Object as small as possible**. If you find yourself wanting a test for something inside a Humble Object, that something likely belongs in the Core.

## Guidelines

- **Keep them boring.** Avoid branches and loops. A Humble Object that needs an `if` for anything other than a precondition check is usually hiding a decision that belongs in the Core.
- **One Humble Object per third-party system, per context.** Where the target system supports transactions, a Humble Object typically spans exactly one of them (representing a Unit of Work or on connection to the third-party system). Do not access two different systems within one Humble Object.
- **One method per interaction.** Target one I/O call per method. On rare occasions, multiple I/O calls per Hunmble Object method can make sense. If the technology supports asynchronous calls, the method is asynchronous.
- **No validation.** A Humble Object returns DTOs or domain objects; the Core validates them if validation is required. Data coming back from a third-party system is input like any other.
- **Unify at the boundary, if you must.** If the same data lives in two systems with slightly different shapes - for example, two DBMS with different table layouts - the Humble Objects may normalize both into the same Core type. That is mapping, and it is allowed.
- **Release resources deterministically.** Humble objects usually own something disposable: a connection, a client, a command, a stream, a file handle. Make the Humble Object disposable, too. Aim for the [Composition Root](./composition-root.mdx) disposing the Humble Object. Especially if the calling Core logic requires dynamic creation of Humble Objects, it can handle them.
- **The same rules apply to UI code.** A view is a Humble Object: it renders and it forwards user interactions. Keep bindings simple, avoid multi-bindings and view-specific converters that carry logic, keep animation triggers dumb, and put no logic in printed reports. Anything you move out of the view is something you can unit-test.

## Where the pattern comes from

Michael Feathers published *The Humble Dialog Box* in 2000. He had built a modal dialog with the logic baked into the window, then found he could not test it without spinning up a UI thread and initializing the whole UI framework first. His fix was to move the logic into a separate class and leave the dialog with nothing but its interactions with the framework - the dialog became humble.

[xUnit Test Patterns](http://xunitpatterns.com/) generalized this into the [Humble Object pattern](http://xunitpatterns.com/Humble%20Object.html): the Humble Object holds the logic that is hard to unit-test and delegates everything else to a testable component.

> Each time the Humble Object is called by the framework, it delegates to the testable component. If the testable component needs any information from the context, the Humble Object is responsible for retrieving it and passing it to the testable component. The Humble Object code is typically so simple that we often don't bother writing tests for it because it can be quite difficult to set up the environment need to run it.

Robert C. Martin arrives at the same construction in chapter 23 of [Clean Architecture](https://www.oreilly.com/library/view/clean-architecture-a/9780134494272/), where Humble Objects at the process boundary are what keeps business logic free of I/O.

:::tip[In .NET Practice]
- Database access is the most common case and has its own page: [Data Access Sessions](./data-access-sessions.md) shows a Humble Object that is simultaneously a Unit of Work.
- Make I/O methods `async` and give them a `CancellationToken` as the last parameter with a default value. Synchronous I/O blocks a thread pool thread and invites thread starvation under load.
- Implement `IAsyncDisposable` (and `IDisposable` where the wrapped resource requires it) and dispose the wrapped `DbContext`, `HttpClient` handler, or `DbConnection`.
- Never let `IQueryable<T>` escape a Humble Object. The moment a caller composes onto the query, the decision about what SQL runs has leaked into the Core, and the query is executed somewhere nobody can see. Materialize inside the Humble Object and return a `List<T>`, an array, or a DTO.
- For HTTP, use `IHttpClientFactory` and a typed client; the typed client is your Humble Object.
:::
