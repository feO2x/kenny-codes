# The Core

<ChackDiagram highlight="core" />

## What belongs in the Core?

Everything that runs in memory.

The Core is the heart of the software. It is written so that it can execute completely in memory, decoupled from every I/O call, which is what makes it cheap to test. It usually consists of three kinds of types:

- **A domain model.** Related types capture the data and, potentially, the rules of the domain. A Humble Object must be able to persist an entity, while the entity itself knows nothing about how that happens. An entity may carry a foreign key property it wouldn't strictly need, but it must not have a method that builds the SQL statement to load or save itself. Whether your entities carry behavior (as in [Domain-Driven Design](https://www.oreilly.com/library/view/domain-driven-design-tackling/0321125215/)) or are plain data holders ([Anemic Domain Model](https://martinfowler.com/bliki/AnemicDomainModel.html)) is your call - CHACK works with both.
- **Services.** These are not persisted. They encapsulate logic that operates on one or more entities. They might be the entry points a framework calls when a request arrives - an HTTP endpoint, a gRPC method, a message subscriber - and they hold the logic for that operation. Services may call other services: an endpoint may call a validator, a calculator, or a mapper.
- **Data Transfer Objects.** Inputs and outputs of endpoints, messages on a broker, configuration values. An anemic domain model usually consists of DTO types. They may be mutable or immutable. If possible, prefer the latter. DTOs that arrive from outside the process are untrusted until your Core has validated them.

:::info[No I/O in the Core]
Everything in this list runs in memory, without touching a disk, a socket, or another process. Make the Core as large and the Humble Objects as small as you can.
:::

## How to write the Core

**Encapsulate the domain.** Implement the required behavior in a way that makes invalid state unreachable - in memory as well as in the database. If a type can only be constructed in a valid state, no caller has to remember the rules.

**Check preconditions, verify postconditions.** Following Bertrand Meyer's [Design by Contract](https://www.eiffel.com/values/design-by-contract/introduction/), validate the parameters a method receives and throw when they are invalid. Verify with automated tests that a method upholds its postconditions and invariants. An advanced developer should study his book [Object-Oriented Software Construction](https://bertrandmeyer.com/OOSC2/).

**Reach for immutability** when a set of values must not change within a part of the code. It prevents accidental state changes and makes concurrent code much easier to follow.

**Name things after the domain.** Types and methods should come out of the ubiquitous language that your domain experts use. Someone reading the Core should recognize the concepts they deal with in their daily work.

**Keep framework details out.** This is the rule that gets broken most often, usually in small, convenient steps:

- Your domain model must not know how it is serialized or persisted. No serialization or O/R mapping attributes on Core types - configure that in separate types, see [Frameworks and libraries](#frameworks-and-libraries).
- Your Core must not know how the application is composed. No DI container attributes, no container types in constructors. Container interactions belong in the [Composition Root](./composition-root.mdx). If absolutely necessary, hide the container in the Core behind an abstract factory.
- When Core code needs to perform an I/O call, introduce an abstraction and a Humble Object that implements it. There is no direct reference to an HTTP client, a database library, a file API, or a message broker client anywhere in the Core.

**Allow coupling inside the Core.** Related Core types may reference each other directly. Introduce indirection via interfaces, abstract base classes, function pointers, etc. only when your code benefits from it. If a service receives a DTO and hands it to a validator, let it call the validator directly - both are then covered by the same Unit Test, with no Test Double in between.

**Make non-determinism explicit.** The current time, new GUIDs, and random numbers change with every call - and so would the results of your tests. When the Core gets these values through an abstraction, each test can decide what they are.

**Cover it with Unit Tests.** They cover not only the happy path but also edge and error cases: a prepared Test Double can simulate failures that are painful to reproduce in an Integration or End-to-End Test (see [Automated Tests](./automated-tests.mdx)).

## Frameworks and libraries

What decides whether a type fits into the Core is I/O, not where it comes from. Your Core will use framework and library types, and that's perfectly fine as long as they don't perform I/O - even types from a data access framework, like enums, value objects, or options types. How strongly your Core depends on a framework is up to you.

The same rule applies to code that extends or configures a framework:

- **Pipes and filters** like middleware, endpoint filters, or pipeline behaviors belong to the Core when they work in memory. When they need I/O, they call an I/O abstraction, just like any other Core type. Registering them and deciding their order in the pipeline is the job of the [Composition Root](./composition-root.mdx).
- **Configuration that doesn't perform I/O by itself** - serialization converters, BSON class maps, O/R mapping configurations - belongs to the Core. Because it runs in memory, you can cover it with Unit Tests, too.
- **Types that perform I/O**, like a database context or a message broker connection, are part of the data access technology. Code that derives from or wraps them is a [Humble Object](./humble-objects.mdx).

## The I/O abstractions belong to the Core

When a Core service needs to call third-party systems, it depends on an abstraction like an interface or an abstract base class. The abstraction describes what the Core requires from the I/O call, in the Core's own vocabulary. A Humble Object implements this abstraction.

This is the [Dependency Inversion Principle](https://www.labri.fr/perso/clement/enseignements/ao/DIP.pdf) at work: the Core owns the abstraction, and the data access layer only implements it.

Give each use case its own abstraction. For example, a single interface with a method for every I/O call across different endpoints (as you can see in many Repository implementations) is a violation of the [Interface Segregation Principle](https://www.cs.utexas.edu/~fares/papers/ISP.pdf). An abstraction works best when it is designed for exactly one consumer - usually one [vertical slice](./vertical-slices.md) - and only contains the members this consumer needs. [Clients and Sessions](./clients-and-sessions.md#one-per-slice-not-one-per-entity) shows what this looks like in practice.

There is one exception: your Core can depend directly on a framework-provided I/O abstraction if it's small, designed for substitution, and ships with ready-made Test Doubles. A logger is a typical example - wrapping it in your own interface only adds another layer without making anything easier to test.
