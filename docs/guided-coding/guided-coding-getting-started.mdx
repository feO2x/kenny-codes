# Guided Coding: Getting Started

This page walks through **the Opinionated Path**: the setup I use, with seven Agent Skills available at [github.com/feO2x/guided-coding](https://github.com/feO2x/guided-coding). Two more skills let you implement a plan yourself while the agent teaches you. See [Guided Learning: Getting Started](./guided-learning-getting-started.mdx).

:::info[Read this first]
The skills are optional. You can follow these steps by hand with Markdown files and git. The skills keep plan structure, filenames, and freezing consistent.

The skills follow the [plan record rules](./plan-record.md) and support both [bundled and custom plan structures](./plan-structures.md). If you want a different workflow, write your own instructions. The phase pages explain the reasoning behind the rules.

Above all: no skill reviews code for you. The Guiding Phase is still yours.
:::

## Install

<Tabs groupId="guided-coding-install">
<TabItem value="skills" label="Agent Skills" default>

Install the skills with the GitHub CLI. The `--agent` flag selects the installation directory. Claude Code reads skills only from its own `.claude/skills` directory, while all other major agents share the `.agents/skills` directory:

```sh
# Claude Code
gh skill install feO2x/guided-coding --all --agent claude-code --scope project

# Any other agent
gh skill install feO2x/guided-coding --all --agent universal --scope project
```

Add `--scope user` to make them available across all your repositories, or name a single skill instead of `--all`. Installed this way, the skills keep their full names:

```text
/guided-coding-setup
```

To update, check for changes first and then update all skills. The GitHub CLI finds the installed skills in both directories on its own:

```sh
gh skill update --dry-run
gh skill update --all
```

The skills follow the [Agent Skills specification](https://agentskills.io/specification), so any agent that implements it can use them. GitHub CLI's skill commands are currently in preview.

</TabItem>
<TabItem value="claude" label="Claude Code plugin">

Add the repository as a marketplace and install the plugin:

```text
/plugin marketplace add feO2x/guided-coding
/plugin install guided-coding@guided-coding
```

Claude Code namespaces plugin skills, so you invoke them with the plugin prefix and a short name:

```text
/guided-coding:setup
```

To update, refresh the marketplace first and then the plugin. Replace `project` with the scope you installed the plugin into:

```sh
claude plugin marketplace update guided-coding
claude plugin update guided-coding@guided-coding --scope project
```

:::warning
Restart Claude Code after updating. Only then does it pick up the updated skills.
:::

</TabItem>
</Tabs>

The repository is also a package for the [Agent Plugins standard](https://agent-plugins.org/). Clients that support the standard can install it directly; the installation and marketplace commands are client-specific. These clients use the skills' full names, so pick the **Agent Skills** tab.

Every skill command below offers the same two tabs. Select your installation method here, and the rest of the walkthrough will show the matching commands.

:::note[Skills run when you ask for them]
Guided Coding depends on you choosing the moment each phase ends, so every skill's description asks the agent to run it only when you explicitly request it. `guided-coding-write-plan` and `guided-coding-review-plan` also accept requests from another Guided Coding skill, because `guided-coding-plan-and-review` invokes them.

A description is a request to the agent, not a lock. Only the Claude Code plugin (through `disable-model-invocation`) and Codex (through `allow_implicit_invocation` in each skill's `agents/openai.yaml`) enforce it for the other skills. All other agents, including Claude Code with skills installed through `gh skill install`, rely on the descriptions alone.
:::

## When to Call What

The Planning Phase comes in two variants. On the **manual path**, one skill writes the plan and another gives you a second opinion when you ask for it. On the **plan-and-review path**, one skill writes the plan and has independent reviewers go over it before you read it. Everything after the Planning Phase is the same.

## The Walkthrough

### Step 0: Set up the repository

Run this once per repository, and again after upgrading to a new Guided Coding version:

<Tabs groupId="guided-coding-install">
<TabItem value="skills" label="Agent Skills" default>

```text
/guided-coding-setup
```

</TabItem>
<TabItem value="claude" label="Claude Code plugin">

```text
/guided-coding:setup
```

</TabItem>
</Tabs>

The skill reads your instruction files, build manifests, scripts, and CI configuration. It then:

- Documents the available feedback-loop commands and what each verifies in the root `AGENTS.md`.
- Creates `ai-plans/AGENTS.md` with the filename conventions and rules for frozen plans and Plan Deviations documents.
- Adds a `## Guided Coding` section to the root `AGENTS.md`, linking to those rules.

When you run it again after an upgrade, it updates outdated Guided Coding instructions and preserves your own rules and existing plans. The [Implementing Phase](./implementing-phase.mdx#the-plan-stays-frozen) explains why the root link is needed.

It lists only commands that can run in the repository. If it finds no feedback loops, it tells you. At least one must be documented before `guided-coding-write-plan` can write a plan.

The defaults are a starting point, and the skill ends with the same customization tips you see here:

- **Plan structure.** `guided-coding-write-plan` uses Rationale, Acceptance Criteria, and Technical Details by default. It also ships the RDAT structure (`rdat-plan-structure.md`), which adds numbered Decisions as a summary for the reviewer. Name a structure file when you invoke `guided-coding-write-plan`, or name it or describe your own structure in `ai-plans/AGENTS.md`. See [Plan Structures](./plan-structures.md).
- **Filenames.** The skills build names from `<timestamp>` (UTC, `YYYY-MM-DD-HHMM`), `<ticket-id>`, and `<short-title>`. Conventions such as a ticket ID format or a maximum length for the short title belong in `ai-plans/AGENTS.md`.
- **Feedback loops.** Plans reference the feedback loops in the root `AGENTS.md` to make acceptance criteria verifiable. Adding or removing one later only means updating that list.
- **Plan review.** An optional `## Plan Review` section in `ai-plans/AGENTS.md` sets the reviewers, their preferred models, and the round limit (default 3). It also controls how to handle findings that challenge your decisions: `collect` (default) reports them for you to decide later; `pause` asks you during the run. See [Automated Plan Review](./automated-plan-review.mdx#configuration).
- **Deviations.** The threshold for what counts as a material deviation can be tightened or relaxed in `ai-plans/AGENTS.md`.

Repository-specific conventions in your `AGENTS.md` files take precedence over the skills' defaults.

The setup skill doesn't choose a plan structure for you, so your plans use the default until you name one. I use RDAT for all my plans, and the rest of this walkthrough does, too. To follow along, add this line to `ai-plans/AGENTS.md`:

```md
Use the RDAT plan structure (`rdat-plan-structure.md`).
```

Read the resulting diff before you commit it. This file steers every future conversation, so it is worth the two minutes. See [What Belongs in a Rules File](./rules-files.md) for how to decide what earns a place there.

### Step 1: Discuss the approach

Start the Planning Phase in a fresh conversation. Describe the context and ask the agent to investigate the codebase before proposing an implementation:

> *"As an experienced .NET architect, investigate the codebase and explain how you would approach this problem."*

Now discuss. Ask why. Push back. Propose alternatives. Ask what it considered and discarded. Keep going until you understand the suggested approach well enough to defend it to a colleague.

Nothing has been created yet at this point - no issue, no branch, no file. That is on purpose. This conversation may well end with "actually, we shouldn't build this", and an untouched repository is the right outcome when it does.

Don't use your agent's built-in planning mode here. See the [Planning Phase](./planning-phase.mdx) for why.

### Step 2: Write the plan

Still in the same conversation:

<Tabs groupId="guided-coding-install">
<TabItem value="skills" label="Agent Skills" default>

```text
/guided-coding-write-plan
```

</TabItem>
<TabItem value="claude" label="Claude Code plugin">

```text
/guided-coding:write-plan
```

</TabItem>
</Tabs>

The skill records the approach you discussed in `ai-plans/<short-title>.md`. It uses the plan structure named in `ai-plans/AGENTS.md`: [RDAT](./plan-structures.md#rdat), if you added the line from step 0. The draft has no timestamp until you freeze it in step 6.

**Run this skill once per plan.** Request revisions with ordinary prompts. Run it again when you need a new plan, such as a follow-up after the Guiding Phase or a plan for another feature.

### Step 3: Further discussion

Read the draft and discuss any problems with the agent:

- Would you approve the plan after reading only its Decisions?
- Does every acceptance criterion describe something you could actually verify?
- Is anything discussed in step 1 missing from the plan?
- Does it reference types, files, or extension points that really exist?
- Is it prescribing implementation steps a senior engineer wouldn't need?

Ask the agent to revise the draft as you go. Expect several rounds of discussion and revision before the plan is ready to freeze.

### Step 4: Review the plan

For larger or riskier plans, add a second opinion from a **fresh conversation** with another agent:

<Tabs groupId="guided-coding-install">
<TabItem value="skills" label="Agent Skills" default>

```text
/guided-coding-review-plan
```

</TabItem>
<TabItem value="claude" label="Claude Code plugin">

```text
/guided-coding:review-plan
```

</TabItem>
</Tabs>

The fresh conversation matters: an agent that just wrote a plan is a poor judge of it. The skill reports findings only and never edits anything. It checks acceptance criteria for verifiability, validates claims about existing types and files, and looks for omissions around error handling, migration, performance, and security.

### Step 5: Further discussion

Take those findings back to the main conversation and work through them. Then ask, repeatedly:

> *"Would you change anything about the plan?"*

This question has caught more problems for me than any review checklist. If the answer suggests useful changes, return to step 3 to discuss and revise the plan. Repeat until you are satisfied.

Repeat steps 3 through 5 as needed. Continue until you and the agent stop finding useful changes to make.

### Alternative to steps 2 to 5: plan and review

Instead of writing the plan and asking for a second opinion yourself, you can let independent reviewers go over the draft before you read it. Still in the same conversation as step 1, run this in place of step 2:

<Tabs groupId="guided-coding-install">
<TabItem value="skills" label="Agent Skills" default>

```text
/guided-coding-plan-and-review
```

</TabItem>
<TabItem value="claude" label="Claude Code plugin">

```text
/guided-coding:plan-and-review
```

</TabItem>
</Tabs>

The skill writes the draft using `guided-coding-write-plan`, then runs independent reviews in place of step 4. After each round, it addresses every finding by changing the plan or rejecting the finding with a reason. It then stops if that round reported no `blocking` or `gap` findings, or if it reached the round limit.

The skill never changes a decision you made explicitly without your approval, and it never freezes the plan. It ends with a report for you to review.

Read the report's list of decision and scope changes first, then read the plan. Discuss and revise them as in steps 3 and 5 until the plan is stable.

After larger revisions, you can run `guided-coding-plan-and-review` again on the existing draft. A re-run starts at round 1 with a fresh round limit and cost, and its reviewers don't see the earlier findings, so a finding you rejected can come back.

[Automated Plan Review](./automated-plan-review.mdx) covers the configuration, the cost, and how to read the report. Once the plan is stable, continue with step 6.

### Step 6: Freeze the plan

If the work should have a tracker issue, create it now, before you freeze. The skill asks for the ticket ID and puts it into the filename, and the stable draft makes a good issue description. Skip this when the work has no ticket; the filename then simply omits the ID.

Then freeze the plan:

<Tabs groupId="guided-coding-install">
<TabItem value="skills" label="Agent Skills" default>

```text
/guided-coding-freeze-plan
```

</TabItem>
<TabItem value="claude" label="Claude Code plugin">

```text
/guided-coding:freeze-plan
```

</TabItem>
</Tabs>

The skill takes the current UTC timestamp from the shell, renames the draft to `<timestamp>-<ticket-id>-<short-title>.md` (or without the ticket ID when there is none), and inserts a `*Frozen at ...*` line below the title. It refuses to overwrite an existing file.

**The freeze ends the Planning Phase.** From this moment the plan is frozen: the only edit anyone may make is ticking an acceptance criterion once the implementation actually satisfies it. Corrections happen through follow-up plans, not edits. See [The Plan Record](./plan-record.md).

Now commit the frozen plan. The skill does not do that for you, so commit it yourself or use a normal prompt, and keep the plan file alone in that commit so the record stays readable.

### Step 7: Implement

Start a fresh conversation and hand over the committed plan:

<Tabs groupId="guided-coding-install">
<TabItem value="skills" label="Agent Skills" default>

```text
/guided-coding-implement ai-plans/2026-08-13-1420-42-cancelled-events.md
```

</TabItem>
<TabItem value="claude" label="Claude Code plugin">

```text
/guided-coding:implement ai-plans/2026-08-13-1420-42-cancelled-events.md
```

</TabItem>
</Tabs>

If you omit the plan path, the skill selects a plan only when exactly one plan has every acceptance criterion unchecked and it has the latest timestamp among all plans in `ai-plans/`. Otherwise, it asks for the path. It refuses to start on a plan that isn't frozen.

Before writing code, the skill checks the plan's assumptions against the existing code. It uses temporary tests or projects when needed, then removes them. It implements the plan and checks off acceptance criteria only after the relevant feedback loops verify them.

If the plan contains an error, the skill may use a workaround under the [four conditions described in the Implementing Phase](./implementing-phase.mdx#when-the-plan-is-wrong). Criteria met through a workaround stay unchecked for your decision in step 8. When no workaround is allowed, the skill stops the affected work, finishes the rest, and reports the problem.

At the end, it reports what it implemented, which feedback loops ran, which criteria remain unchecked and why, each workaround, and each problem it did not work around. It does not commit anything or open a pull request unless you ask it to.

You can also use a plain prompt:

> *"As an experienced .NET developer, implement plan `ai-plans/2026-08-13-1420-42-cancelled-events.md`."*

The skill adds a check of the plan's assumptions and consistent rules for handling errors in the plan. Its report makes these problems easier to review.

Then let it run. The frozen plan and your feedback loops are what keep the agent on track - see the [Implementing Phase](./implementing-phase.mdx).

### Step 8: Guide

This is the phase you actually spend most of your time in. Read every changed file, evaluate the design, run the tests yourself, and smoke-test the app. Optionally add a code review from a fresh agent conversation.

Start with what the agent reported in step 7:

- **Each workaround** → accept it and check off the acceptance criteria it left unchecked, or reject it and write a follow-up plan.
- **Each problem the agent did not work around** → a targeted prompt when solving it changes no plan decision, a follow-up plan when it does.

Then decide on what you found yourself:

- **Small issue** → prompt the agent to fix it. Back to the Implementing Phase.
- **Large issue** (wrong data structure, misused framework mechanism, design flaw) → back to the Planning Phase. Steps 1 through 6 again, producing a follow-up plan with the same ticket ID.

The review of the pull request can send you back here, too: when it leads to another follow-up plan, step 9 shows how the Plan Deviations document follows. The [Guiding Phase](./guiding-phase.mdx#workarounds-and-reported-problems) page covers what to look for.

### Step 9: Write and review the deviations, then open the PR

Once you are satisfied with the implementation, run:

<Tabs groupId="guided-coding-install">
<TabItem value="skills" label="Agent Skills" default>

```text
/guided-coding-write-deviations
```

</TabItem>
<TabItem value="claude" label="Claude Code plugin">

```text
/guided-coding:write-deviations
```

</TabItem>
</Tabs>

The skill reads every plan for the issue, inspects all implementation changes and the commit history, and decides whether a Plan Deviations document is needed:

- If follow-up plans exist, it **always** writes a Plan Deviations document that summarizes which earlier decisions they superseded and where the implementation ended up.
- With a single plan, it writes one only when the implementation materially departed from an explicit decision. Routine implementation choices still don't count.
- With a single plan and no material deviations, it reports that conclusion and writes nothing.

If a Plan Deviations document already exists for the work item and hasn't been merged into the target branch yet, the skill renames it with a new timestamp and rewrites it, so it still sorts after all plans. A merged document is frozen: the skill tells you so and leaves it alone.

The skill only writes the document and reports its path. It does not commit anything, create a pull request, or publish the contents. Review the draft and revise it with ordinary prompts until you accept it.

After approval, either finish the work yourself or use a normal prompt:

> *"Please commit the Plan Deviations document, create a pull request, and use the document's contents as the pull request description."*

When no document was required, create the pull request normally.

If the pull request review leads to another follow-up plan, go through the Planning, Implementing, and Guiding Phases for it as usual, then run `guided-coding-write-deviations` again before the merge. The document stays editable until it is merged into the target branch, so it can still cover that plan.

The goal: **a reviewer should need to read only the issue's first plan and, when one exists, the Plan Deviations document to understand the whole change.** Follow-up plans always cause that final document to be created, so their decisions are not hidden from the reviewer.
