# 1. Planning Phase (~ 30–90 minutes)

<GuidedCodingDiagram highlight="planning" />

## Let the agent plan with you

Start a new conversation with your coding agent and work out a plan together. Discuss the requirements and the technical approach:

- **Don't use your Coding Agent's "planning mode"**. I don't use the built-in "planning mode" of coding agents. There is no iteration involved, and plans typically do not end up in your git repo. The default Agent mode is enough, you steer the conversation actively.
- **Give the agent a role.** I use something like "As an experienced .NET architect" in my first prompt of the planning phase. This focuses the agent on planning rather than jumping into implementation. Assigning roles tends to produce better results in my experience.
- **Discuss the feature.** Ask the agent how it would approach the problem. Review its suggestions about elements like design, refactorings, testing, and performance. Bring your own thoughts and questions to the table - this is a conversation, not delegation.
- **End with repeated sanity checks.** At the end of the planning phase, I typically ask *"Would you change anything about the plan?"* This often catches things I didn't think of. Do this repeatedly until the plan stabilizes.
- **Commit the plan as a markdown file in the git repo.** Plans serve as a project-specific decision record. They form a history, similar to Event Sourcing.

:::tip[The Opinionated Path]
I open a **fresh conversation** and describe the context, then ask for an investigation rather than a solution:

> *"As an experienced .NET architect, investigate the codebase and explain how you would approach this problem."*

Then I discuss this with the agent until I have understood the suggested approach. Nothing is created during this conversation - no issue, no branch, no file. Sometimes it ends with the conclusion that the change isn't worth making, and then an untouched repository is exactly what I want to be left with.

:::

## Plan Structure

Whatever structure you choose, a plan needs at least three sections, which are quite common in Agile Development:

1. **Rationale** - Why do we want to build this? Why is this feature needed or why does this bug need fixing? This gives the agent context for the greater goal.
2. **Acceptance Criteria** - Bullet points that must be fulfilled for the feature to be approved. The agent in the Implementing Phase will use these to check off each aspect of the feature after it's been implemented.
3. **Technical Details** - Important parts of the codebase, extension points, types to modify or add, and design direction.

These three are the minimum, not the limit. What matters is that the plan states *why*, states *what must be true when it's done* in a way you can actually verify, and gives enough technical direction that a senior engineer - or a competent agent - can implement it without guessing at your intent. Once plans grow, it helps to pull the important choices into a section of their own, so a reviewer can approve the plan by reading just that. [Plan Structures](./plan-structures.md) describes the default structure, RDAT with its numbered Decisions, and how to bring your own.

Keep plans focused. With Anthropic models in particular (Opus, Sonnet), plans tend to become very detailed with implementation phases and step-by-step instructions that the agent doesn't actually need. The models are smart enough to figure out the implementation order themselves. A plan that's too detailed can actually steer the agent in the wrong direction, because if you missed something, the overly prescriptive structure leaves no room for the agent to adapt. Therefore, use AGENTS.md or a skill to limit the plan size.

A plan is not an epic, a user story, or an initiative - it should contain technical details. You should have technical knowledge to discuss and review these plans effectively.

:::tip[The Opinionated Path]
Once the approach is settled, I run `/guided-coding-write-plan` in the same conversation. It writes the draft to `ai-plans/<short-title>.md`, using the plan structure named in `ai-plans/AGENTS.md` - [RDAT](./plan-structures.md#rdat) in all my repositories. Freezing the plan adds the timestamp to its filename.

The skill records the approach you have already discussed. Settle that approach before asking it to write the plan.

I run it **once per plan**. I request revisions with ordinary prompts, such as "tighten the third acceptance criterion" or "we discussed X but it's missing". I run the skill again when I need a new plan, such as a follow-up after the Guiding Phase.

For larger plans, I run `/guided-coding-plan-and-review` instead. It calls `guided-coding-write-plan` itself and then has the draft reviewed before I read it - more on that in the next section.

The filename convention and the reasoning behind it live on [The Plan Record](./plan-record.md) page.
:::

## Reviewing the Plan

The plan is the cheapest place to catch a bad idea. Fixing a design flaw in a plan costs a paragraph; fixing it after implementation costs a Guiding Phase, a follow-up plan, and another implementation run.

So review it properly:

- **Read it yourself.** Do you understand every technical decision in it? If not, ask the agent to explain, and keep asking until you do.
- **Check that acceptance criteria are verifiable.** "The API is fast" is not a criterion. "The benchmark shows no additional allocations on the happy path" is.
- **Check the claims.** Agents confidently reference types, files, and extension points that don't exist. Verify the ones the design hinges on.
- **Get a second opinion.** For larger or riskier plans, I open a fresh conversation with another agent and have it review the draft. A fresh agent can catch problems the planner missed, such as an acceptance criterion that cannot be verified or an unhandled failure case.
- **Ask the closing question, repeatedly.** *"Would you change anything about the plan?"* Keep asking until the answer stops producing useful changes.

### Letting independent reviewers go first

Independent reviewers can review the draft before you read it. These agents have not seen your planning conversation. After each round, the planner addresses their findings. If another round is needed, new reviewers check the revised draft. You then review the plan and a report of what was found and changed.

This never replaces your own review. The reviewers can check a plan against the code. They cannot tell whether it solves the problem you actually have, and they don't know which decisions you made deliberately. So two rules keep you in charge: the agent never changes a decision you made explicitly without your approval, and the automated review ends where your review begins.

### A cycle, not a checklist

Discuss, review, and revise the draft as often as needed. Use ordinary prompts to request changes. The Planning Phase ends when you agree that the plan is ready for implementation.

If that sounds like a lot of conversation for one markdown file, it is. That is where the 30 to 90 minutes go, and it is the cheapest hour in the whole workflow.

:::tip[The Opinionated Path]
For larger or tougher plans, I use `/guided-coding-review-plan` in a **fresh conversation** with another coding agent. It reports findings only and never edits the plan - it checks acceptance criteria for verifiability, validates claims about existing code, and judges whether relevant risks like error handling, migration, performance, and security boundaries were considered.

Then it's back to the main conversation for another round. There is a constant back and forth between me and the main agent until both of us are satisfied.

When I want the reviewers to go first, I run `/guided-coding-plan-and-review` right after the discussion, **in the same conversation**, in place of `/guided-coding-write-plan`. It writes the draft, runs review rounds with reviewers in fresh contexts, and stops with a report. It never changes a decision I made explicitly without asking me, and it never freezes the plan: my own review begins where it ends. I start with the report's list of decision and scope changes, then read the plan as usual. [Automated Plan Review](./automated-plan-review.mdx) covers configuration, cost, and how to read the report.
:::

## Ending the Phase

The Planning Phase ends with a deliberate act: you freeze the plan and commit it.

That moment matters more than it looks. Up to that point the plan is a draft and anything can change. After it, the plan is **frozen** - a record of what you decided at that moment. You do not edit it later to match what actually happened. If the decision turns out to be wrong, you write a follow-up plan that supersedes it. If the implementation ends up somewhere else, you write a Plan Deviations document that explains why.

The only edit permitted on a frozen plan is ticking an acceptance criterion from `- [ ]` to `- [x]`, and only once the implementation genuinely satisfies it.

This is what makes `ai-plans/` a decision record rather than a pile of stale documents. [The Plan Record](./plan-record.md) explains the rules and the reasoning in full.

:::tip[The Opinionated Path]
If the work has a ticket, I create it right before freezing, so the ticket ID can go into the filename. The stable draft doubles as the issue description.

Then I run `/guided-coding-freeze-plan`. It takes the current UTC timestamp from the shell, renames the draft to `<timestamp>-<ticket-id>-<short-title>.md`, and inserts a `*Frozen at ...*` line below the title. It refuses to overwrite an existing file, and it does not commit.

The freeze is the moment the Planning Phase ends. Afterwards I commit the frozen plan, myself or with a normal prompt, keeping the plan file alone in that commit.
:::
