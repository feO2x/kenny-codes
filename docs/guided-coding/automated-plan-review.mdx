# Automated Plan Review

The [Planning Phase](./planning-phase.mdx#reviewing-the-plan) recommends a second opinion from an agent in a fresh conversation, because an agent that just wrote a plan is a poor judge of it. Doing that by hand means opening a new session, running the review, carrying the findings back, and starting over after larger revisions.

`guided-coding-plan-and-review` automates that loop. It writes the plan draft, has independent reviewers in fresh contexts review it in rounds, addresses their findings, and reports back. You read a plan that has already been through several reviews.

It does not replace your own review. It ends exactly where your review begins: it never freezes the plan, and it never changes a decision you made explicitly without your approval.

## When to run it

Run it **after the discussion, in the same conversation**, in place of `guided-coding-write-plan`. The agent running the skill is the **planner**. It needs the conversation to identify which decisions you made explicitly. The reviewers do not see the conversation; they assess the written plan, just as the implementing agent will.

Without a draft, the skill invokes `guided-coding-write-plan` to write one and passes on any plan structure you named. If you already have a draft, name it. Otherwise the skill picks up an uncommitted draft in `ai-plans/` only if it clearly belongs to the work you discussed, and asks you when several could match.

Options you specify when running the skill override the configuration for that run. For example, to pause when a reviewer challenges one of your decisions:

## Configuration

The skill reads an optional `## Plan Review` section in `ai-plans/AGENTS.md`:

```md
## Plan Review

- Reviewers: two, one on GPT-6.1-Sol High and one on Opus 5.5 High
- Round limit: 3
- User decisions: collect
```

Use the model names supported by your coding agent. If a configured model isn't available, the reviewer uses the agent's default model, and the report tells you so.

Reviewers on different models tend to notice different things, which is why the example uses two.

The defaults are one reviewer on the coding agent's default model, a round limit of 3, and `collect`. Any option you omit from both the command and the configuration uses its default.

### Your decisions: `collect` or `pause`

Reviewers sometimes challenge a decision you made explicitly in the conversation. The planner never changes such a decision on its own. What happens instead depends on the policy:

- **`collect`** (default) - the run continues, and the finding is reported as open for you to decide.
- **`pause`** - the round stops, the planner asks you, and it continues after you answer.

`collect` lets the run finish while you do something else. `pause` costs you attention during the run, but the remaining rounds review the plan with your answer already in it.

## How a run works

Each round starts a new agent for each configured reviewer, running them in parallel when supported. Agents from earlier rounds are never reused. Each reviewer receives:

- The instruction to run `guided-coding-review-plan` on the draft and classify every finding.
- The paths of earlier documents for the same work.
- From round 2 onwards, all earlier findings and how the planner addressed them.

Reviewers may raise new findings. They may repeat a rejected finding only if they give a new reason for it.

### Finding classes

- **`blocking`** - a false assumption, an open decision, an acceptance criterion that cannot be verified, or a contradiction with the code.
- **`gap`** - a missing scenario or fact.
- **`nit`** - everything else.

### Addressing findings

The planner addresses findings in every class. It follows the `collect` or `pause` policy for findings that challenge your explicit decisions. For other findings, it either changes the plan or rejects the finding with a one-line reason. When findings contradict each other, it applies at most one. It combines duplicate findings and keeps the most severe classification: `blocking`, then `gap`, then `nit`.

Apart from your explicit decisions, the planner may change anything in the plan, including decisions it made alone and the scope. That freedom is what makes the rounds useful, and it is also why the report lists those changes separately for you.

Revisions must follow the selected plan structure. The planner keeps review commentary out of the plan and does not turn `nit` findings into new rules.

### When the run stops

After addressing the findings, the planner ends the run if that round reported no `blocking` or `gap` findings. Otherwise, it starts another round unless it has reached the round limit. Findings classified only as `nit` do not trigger another round.

Reaching the round limit can leave substantive findings open. The report tells you, and those are the first findings to look at.

### Cost

Every reviewer in every round is a separate subagent run with its own context, and each one reads the plan, your repository instructions, and the code the plan discusses. A run therefore costs at most **reviewers × rounds** subagent runs, plus one replacement for each reviewer that fails. Two reviewers and a round limit of 3 mean up to six reviews. A run that stops early costs less.

## Reading the report

The report is where your review begins. Start with the **list of decision and scope changes the planner applied**. It is separate from the findings, so you can confirm each change without comparing versions of the plan. It includes changes you approved during a `pause`. Confirming these is part of your own review: they are choices the planner made after you last read the plan.

Then go through the rest:

- **Every finding** with its round, class, a one-line summary, and its resolution: applied, rejected with the reason, or open for you. Read the rejected ones, too. A rejection you disagree with is a discussion worth having.
- **The reviewers and the models actually used.** If a configured model was unavailable, the report names the coding agent's default model used in its place.
- **The plan's word count** before and after review. A plan that grew a lot deserves a second look at its level of detail.
- **Whether the plan changed after the last round.** The independent reviewers have not checked those changes.

### When the run doesn't complete a review

Some outcomes are not a completed review, and the report says so:

- **No independent reviewers are available.** Reviewers must not share the planning conversation, so they run as subagents, threads, or separate sessions. If your coding agent offers none of these, the skill reports the plan path, states that no review ran, and stops. It never reviews the plan in its own context instead. Run `guided-coding-review-plan` in a fresh session.
- **`guided-coding-write-plan` cannot be invoked.** The skill never writes a plan without it, so it stops and asks you to run `guided-coding-write-plan` first. Afterwards, run `guided-coding-plan-and-review` again, and it picks up the draft.
- **A round is incomplete.** If a reviewer fails or times out, the skill starts one replacement. If that fails too, the skill addresses the findings it already has, reports the incomplete round, and stops.
- **The plan changed after the last round.** The independent reviewers have not checked the planner's final revisions. Read them with particular care.

## After the run

From here on, the Planning Phase continues as usual: you read the report and the plan, discuss them, and ask the agent to revise the plan with plain prompts. The closing question still applies: *"Would you change anything about the plan?"*

After larger revisions, you can run `guided-coding-plan-and-review` again on the existing draft. A re-run starts at round 1 with a fresh round limit and the same cost as a first run. Its reviewers don't see the findings of earlier runs, so a finding you rejected before can come back. Treat it like any other finding: if your reason still holds, reject it again.

Once the plan is stable, freeze it as described in [Guided Coding: Getting Started](./guided-coding-getting-started.mdx#step-6-freeze-the-plan).

:::warning
The reviewers are subagents that run with your permissions. See [Security: Be Vigilant](./security.md).
:::
