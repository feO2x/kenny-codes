# Document Guided Coding 2.1.0

*Frozen at 2026-11-18T04:24Z*

## Rationale

Guided Coding 2.1.0 (`~/Code/guided-coding`, tag `2.1.0`) adds `guided-coding-plan-and-review`, the RDAT plan structure, premise checks with bounded workarounds in the implement skills, and Plan Deviations documents that stay editable until merged. The docs in `docs/guided-coding/` describe 2.0.0 and now contain wrong statements about the skills.

## Decisions

- **D1 – Page structure.** Add three pages: `plan-structures.md` (Plan Structures), `automated-plan-review.mdx` (Automated Plan Review), and `release-notes.md` (Release Notes). Sidebar order: Overview, Guided Coding: Getting Started, Guided Learning: Getting Started, Planning Phase, Implementing Phase, Guiding Phase, The Plan Record, Plan Structures, Automated Plan Review, What Belongs in a Rules File, Finding the Right Plan Size, Security, Communication, Comparison, Release Notes. Reason: details that several pages refer to get one home, and Getting Started stays a walkthrough.
- **D2 – Version history.** "What Changed in Version 2.0.0" leaves `index.mdx`. The overview links to Release Notes in one sentence. Release Notes has a 2.1.0 and a 2.0.0 section that summarize the matching `CHANGELOG.md` entries and links to the CHANGELOG on GitHub. Reason: the overview should not grow with every release.
- **D3 – Plan structures.** Plan Structures explains the default structure, RDAT (why Decisions exist, Decision IDs, the Out-of-Scope Decision, checking assumptions against the code, each section adding information), the optional `## Notes for the Guided Learning Teacher` section, and how to pick a structure per plan (name it when invoking `guided-coding-write-plan` or `guided-coding-plan-and-review`), per repository (name it in `ai-plans/AGENTS.md`), or bring your own file. The method text in Planning Phase keeps Rationale, Acceptance Criteria, and Technical Details as the minimum and links to Plan Structures. The Opinionated Path uses RDAT: Getting Started step 0 tells readers to add ``Use the RDAT plan structure (`rdat-plan-structure.md`).`` to `ai-plans/AGENTS.md`, because setup does not name a structure. Statements that the skills assume or only support the three-section structure are removed.
- **D4 – Plan and review in the method.** Planning Phase "Reviewing the Plan" adds the method-level idea: independent reviewers in fresh contexts can review a draft in rounds before you read it, and this never replaces your own review. The docs say explicitly that `guided-coding-plan-and-review` runs after the discussion, in the same conversation, never changes your explicit decisions without your approval, and ends where your review begins.
- **D5 – Plan and review in Getting Started.** Steps 2–5 keep the manual path. A subsection after step 5 describes the plan-and-review path as an alternative to steps 2–5, so the install Tabs are never nested in other Tabs. In the plan-and-review path, step 2 runs `guided-coding-plan-and-review` instead of `guided-coding-write-plan`, step 4 (`guided-coding-review-plan`) is dropped, and the cycle is reading the report and the plan, then further discussion with revisions by prompt. After larger revisions, you can run `guided-coding-plan-and-review` again on the existing draft; a re-run starts at round 1 with a fresh round limit and cost, and its reviewers do not see earlier findings, so rejected findings can return. The prose below the timeline covers both variants: in the plan-and-review path, the repetition is reading, discussing, and revising by prompt, plus optional re-runs. Automated Plan Review covers configuration, invocation options that override it (e.g., `pause` for one run), finding classes, `collect`/`pause`, models per reviewer, cost (reviewers × rounds, plus replacements), the stopping rule (a round without `blocking` or `gap` findings ends the run, `nit`s alone never start another round, and reaching the round limit can leave substantive findings open), and how to read the report, starting with its separate list of decision and scope changes the planner applied, which you confirm in your own review. That includes a configured model that was unavailable and replaced by the harness default, which the report names, and the outcomes that are not a completed review: no independent reviewers available (no review runs; use `guided-coding-review-plan` in a fresh session), `guided-coding-write-plan` not invocable (the skill stops and asks you to run it first), an incomplete round after a failed replacement reviewer, and plan changes after the last round that are unreviewed.
- **D6 – Timelines.** `GuidedCodingSkillTimeline` and `GuidedLearningSkillTimeline` each get an optional `variant` prop (`'manual'` default, `'plan-and-review'`). In both components, the `plan-and-review` Planning card has these steps: Discuss the approach, `guided-coding-plan-and-review`, Read the report and the plan, Further discussion ("Would you change anything about the plan?"), `guided-coding-freeze-plan`. Its loop spans Read the report and the plan to Further discussion, labeled "repeat until it stabilizes". In the Guided Learning card, the step descriptions keep the senior developer involved, as the manual card does. The other cards are identical in both variants. Each component and variant has its own title ID and accessible description. Both Getting Started pages show both variants in Tabs.
- **D7 – Plan issues during implementation.** Implementing Phase replaces "stop and go back to the Planning Phase" with a section on wrong plans: check the plan's premises against the code before coding, the four conditions under which a workaround is allowed, criteria met only through a workaround stay unchecked, and otherwise stop only the affected work and report it. Getting Started step 7 matches, and also states that the skill picks a plan on its own only when exactly one plan has all criteria unchecked and that plan has the latest timestamp, and asks for the path otherwise.
- **D8 – Guiding Phase duties.** Guiding Phase adds: judge each reported workaround (accept and check off the criterion, or reject and write a Follow-Up Plan), decide on each reported problem the agent did not work around (a targeted prompt when no plan decision changes, a Follow-Up Plan when one does), and re-run `guided-coding-write-deviations` when PR review leads to another Follow-Up Plan. Getting Started step 8 matches.
- **D9 – Plan Record.** The Plan Record and every other page state the 2.1.0 rule: one Plan Deviations document per work item, renamed with a new timestamp on each update so it sorts after all plans, frozen once merged into the target branch. To redo a merged one, delete it and run the skill again. "Frozen once committed" disappears everywhere. The unchecked-criterion rule adds that a reviewer may also check off a criterion met through a workaround they accept. The Opinionated Path "Guardrails" state that `guided-coding-write-deviations` renames and rewrites an unmerged document, never changes a merged one, and stops without changing anything when it finds several Plan Deviations documents for the work item, a filename collision, or cannot fetch or resolve the target branch, because a stale branch cannot prove that a document is unmerged. Its "Skills" list includes `guided-coding-review-plan` and `guided-coding-plan-and-review`.
- **D10 – Root `AGENTS.md` guidance.** The docs recommend what `guided-coding-setup` creates: frozen-plan rules in `ai-plans/AGENTS.md`, and a `## Guided Coding` section in the root `AGENTS.md` that only links to it. The method text explains that this link is what makes agents that skip nested instruction files read the rules. This replaces the "When you implement a plan" snippets in `implementing-phase.mdx` and `rules-files.md` and corrects the description of setup in Getting Started step 0 and the Rules Files callout.
- **D11 – Skill facts.** Correct skill counts (seven Guided Coding skills plus two Guided Learning skills, nine in total), including `security.md`. Replace "All skills are manually invoked" with: every skill's description asks the agent to run it only on explicit request; `guided-coding-write-plan` and `guided-coding-review-plan` also allow requests from another Guided Coding skill. Only the Claude Code plugin (`disable-model-invocation`) and Codex (`allow_implicit_invocation` in `agents/openai.yaml`) enforce this for the other skills; all other agents, including Claude Code with skills installed through `gh skill install`, rely on the descriptions alone. Security mentions that `guided-coding-plan-and-review` starts subagents that run with your permissions. Getting Started step 0 customization tips match the 2.1.0 setup skill (plan structure incl. RDAT, plan review config). Comparison no longer claims that the skills create issues or commit plans.
- **D12 – Guided Learning.** Guided Learning: Getting Started describes the premise check, temporary tests or projects that the agent removes again ("the agent makes no lasting changes to your repository" replaces "never changes your repository"), workarounds discussed with you before they go into the code, pausing and asking you when no workaround is allowed, the summary for the reviewer, and the teacher-notes section of RDAT, which `guided-coding-write-plan` adds only when the planning conversation says the plan will be taught. The claim that show-me suggests switching to coach-me is removed. The page offers the plan-and-review path as an alternative for the Planning Phase: writing the plan together with the senior developer stays the better option, but when that is not possible, `guided-coding-plan-and-review` saves time, and the senior developer checks the reviewed plan and its report before it freezes.
- **D13 – Rules files.** What Belongs in a Rules File uses the plan structure choice and the `## Plan Review` section as examples of guidance that belongs in `ai-plans/AGENTS.md`.
- **D14 – Out of scope.** A 2.1.0 blog post, changes to existing blog posts (`blog/2026-02-28-guided-coding/`), and the README of the guided-coding repository.

## Technical Details

- **Source of truth for skill behavior:** the skills in `.claude/skills/` (installed from tag `2.1.0`), plus `README.md` and `CHANGELOG.md` in `~/Code/guided-coding`. `guided-coding-plan-and-review/SKILL.md` and `guided-coding-write-plan/assets/rdat-plan-structure.md` are the main references for D3–D5.
- **Two layers:** method text is tool-independent; skill names and exact prompts go into `:::tip[The Opinionated Path]` callouts (see `index.mdx`). Follow this for D4, D7, and D8. Voice: explain the reason for a rule where the reader needs it, don't lecture.
- **Sidebar:** autogenerated from `sidebar_position` frontmatter (`sidebars.ts`). D1 requires renumbering every page after The Plan Record.
- **Skill invocations:** only the two Getting Started pages show invocations in `<Tabs groupId="guided-coding-install">` blocks with Agent Skills and Claude Code plugin tabs. Method pages and callouts name skills inline (`/guided-coding-write-plan`). Keep that split: Automated Plan Review uses the Tabs for its invocation examples, Plan Structures and the method pages do not.
- **Links:** use relative Markdown links (`./plan-structures.md`). Never hardcode `/docs/...` hrefs in components, see the preview note in the root `AGENTS.md`. No inbound links to the removed `#what-changed-in-version-200` anchor exist.
- **Timelines (D6):** `src/components/GuidedCodingSkillTimeline/index.tsx` and `src/components/GuidedLearningSkillTimeline/index.tsx` build their SVGs from a `cards` array; `loop: {from, to}` indexes steps within a card. Their title IDs (`guided-coding-skill-timeline-title` and `guided-learning-skill-timeline-title`, used by `aria-labelledby`) are hardcoded today. Docusaurus Tabs render inactive panels hidden, not unmounted, so both variants are in the DOM at once; derive the ID from the variant. Keep the output identical when no prop is passed. Use one Tabs `groupId` for the variants on both pages, separate from the install Tabs, so the reader's choice carries over between the two pages but not to the install method.
- **Configuration example (D5):** show a `## Plan Review` section with two reviewers on different models, `Round limit: 3`, and `User decisions: collect`, and note that model names are harness-specific.
